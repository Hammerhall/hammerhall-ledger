## Зачем писать тест с нуля

Первая задача на проекте, и без тестов её не примут. Ты открываешь IDE,
а в `src/test/java` пусто или лежат чужие файлы. Где создать свой файл?
Что написать первой строкой? Как назвать метод?

Интернет отвечает охотно, но часто из прошлого. Многие примеры написаны
для JUnit 4, и в песочнице серии они не скомпилируются. А тест,
собранный из чужих кусков без понимания, на ревью не защитишь. Ревьюер
спросит, почему в ожидании число, а не константа, и почему тестов
четыре, а не один. Ответ должен быть твой.

Поэтому в этой статье — один класс тестов от пустого файла до зелёного
отчёта, по строке. Модульный тест, как в таблице из статьи 1, проверяет
один класс без базы, сети и Spring. Это самый быстрый и самый частый
вид тестов.

Пример — тот же зачёт по сроку. Сдал до срока или ровно в срок —
получаешь 100. Опоздал не больше чем на сутки — 50. Опоздал сильнее — 0.

Считает балл статический метод `DeadlineScore.score(deadline, submittedAt)`.
Он принимает срок и время сдачи, оба `Instant`, и возвращает балл. Мы
напишем четыре теста, по одному на каждый случай. Случай, когда срока
нет (`null`), разберём в продолжении серии.

Песочница — та же `testy`, что в [статье 1 «Зачем тесты и чего от тебя ждут на проекте»](https://hammerhall.io/ledger/testing/1-why-tests).
В ней уже есть `DeadlineScore`, `ManualCheck`, тест `TestyApplicationTests`
от Initializr и наш `DeadlineScoreTest` с одним тестом. Содержимое
`DeadlineScoreTest` мы напишем заново. Песочницы нет — как её собрать,
сказано в конце статьи 1.

В коротких примерах ниже нет строк `import`. Полные файлы — в конце
статьи.

## Часть 1. Пустой файл, первый метод

### Где создать файл

Тест к классу лежит в `src/test/java`, в том же пакете, что и класс.
Называется он именем класса плюс `Test`: по этому окончанию Maven его
и находит (статья 1). Для `DeadlineScore` из пакета `example.testy.score`
путь такой: `src/test/java/example/testy/score/DeadlineScoreTest.java`.

В IDE найди в дереве проекта папку `src/test/java` и создай в ней пакет
`example.testy.score`, если его ещё нет. В пакете создай класс. Пакет
пишется через точки, вложенные папки IDE сделает сама.

Тот же пакет нужен по двум причинам. Тест видит то, что объявлено
без модификатора доступа. И найти его легко: тот же путь, только
верхняя папка другая. Ревьюер будет искать его именно там.

### Пустой класс

```java
package example.testy.score;

class DeadlineScoreTest {
}
```

Это уже настоящий класс тестов, только тестов в нём пока ноль. Заметь:
перед `class` нет `public`. В курсах классы почти всегда публичные,
и рука тянется его написать.

Тестовому классу `public` не нужен. JUnit 5 и 6 находят и запускают
классы и методы без него, нельзя только `private`. Документация JUnit
прямо советует `public` не писать, если нет особой причины. Работе он
не мешает, это просто лишнее слово.

### Метод с пометкой @Test

```java
class DeadlineScoreTest {

    @Test
    void beforeDeadlineGetsFull() {
        // …
    }
}
```

`@Test` — аннотация, пометка для инструмента (статья 1). JUnit ищет
в классе методы с этой пометкой и каждый запускает как отдельный тест.
Импорт у неё такой: `org.junit.jupiter.api.Test`.

Сам метод устроен просто:

* **`void`** — тест ничего не возвращает, так требует JUnit. Итог
  теста — не значение, а исход: прошёл или упал.
* **Без параметров.** Тест запускает JUnit, а не твой код, и нашим
  тестам параметры не нужны. Бывают тесты, которые получают данные
  строками таблицы. О них расскажет продолжение серии, а первое
  знакомство есть в [статье 0 «Что нужно знать до Spring»](https://hammerhall.io/ledger/articles/0-before-spring)
  цикла «От Java к Spring Boot».
* **Без `public`** — как и класс.
* **Имя** — о нём в части 3.

⚠️ В интернете ты увидишь `import org.junit.Test`, `public` у класса
и у каждого метода и проверки вида `Assert.assertEquals(…)`. Это
JUnit 4, и в нём `public` был обязателен. В песочнице JUnit 6, а пишется
он как пятый: аннотации из `org.junit.jupiter.api`, без `public`,
проверки на AssertJ. Четвёртого JUnit в песочнице нет, и такой тест
не скомпилируется: `package org.junit does not exist`.

Хуже, если JUnit 4 приедет в проект вместе с чужой библиотекой. Тогда
тест скомпилируется, но сборка, скорее всего, его не запустит, а IDE —
может. Снова «зелёный только в IDE», как в статье 1. Тесты JUnit 3 и 4
запускает особый движок JUnit для старых тестов, Vintage, а его
в песочнице нет. Проверка та же: добавил тест, и число тестов в отчёте
выросло ровно на столько же.

### Константа DEADLINE

Первые строки внутри класса:

```java
    // полночь 13 октября по Москве
    private static final Instant DEADLINE = Instant.parse("2026-10-12T21:00:00Z");
```

Срок нужен всем четырём тестам, и он у всех один. Можно написать его
в каждом тесте заново, но это четыре одинаковые строки. Читателю
придётся сверять, правда ли они одинаковые. Поэтому срок —
**константа**: значение с именем, записанное один раз. Тогда в каждом
тесте видно только то, чем он отличается от соседей, — время сдачи.

Каждое слово объявления — со смыслом.

* `private` — константа нужна только этому классу.
* `static` — она одна на весь класс. JUnit перед **каждым** тестом
  создаёт новый объект тестового класса: так тесты не влияют друг
  на друга через поля. Обычное поле создавалось бы заново для каждого
  теста. Поле со `static` одно на всех, и по нему сразу видно: значение
  общее, а не состояние одного теста.
* `final` — присвоить константе другое значение нельзя. Ни один тест
  не передвинет срок для остальных.
* Имя заглавными буквами через подчёркивание — так в Java принято
  называть константы.

И ещё одно свойство — самого `Instant`: он **неизменяемый**.
`DEADLINE.plus(…)` не сдвигает срок, а возвращает новый момент времени.
Поэтому одну константу можно спокойно делить между тестами: испортить
её нельзя.

## Часть 2. Тело теста: дано — когда — тогда

### Три блока

Вот первый тест целиком:

```java
    @Test
    void beforeDeadlineGetsFull() {
        Instant submittedAt = DEADLINE.minus(Duration.ofMinutes(1));

        int score = DeadlineScore.score(DEADLINE, submittedAt);

        assertThat(score).isEqualTo(100);
    }
```

Он состоит из трёх блоков, разделённых пустыми строками.

* **Дано** — подготовка. Срок уже есть, это константа. Время сдачи —
  за минуту до срока: `minus` вычитает отрезок времени `Duration`
  (статья 1), а `ofMinutes(1)` задаёт одну минуту.
* **Когда** — ровно одно действие, которое проверяем: вызов `score`.
* **Тогда** — проверка: балл равен 100.

Схема так и называется, по трём блокам: **«дано, когда, тогда»**.
В английских текстах её зовут given, when, then или arrange, act, assert.
Пустые строки здесь не для красоты. По ним глаз сразу находит, где
подготовка, где действие, а где проверка.

Некоторые команды пишут ещё комментарии `// given`, `// when`, `// then`.
В коротком тесте хватает пустых строк.

Во втором тесте блоков два:

```java
    @Test
    void onDeadlineIsStillOnTime() {
        int score = DeadlineScore.score(DEADLINE, DEADLINE);    // сдал ровно в срок

        assertThat(score).isEqualTo(100);
    }
```

Подготавливать нечего: сдал ровно в срок, значит, время сдачи и есть
`DEADLINE`. Блок может быть пустым, а порядок менять нельзя. Проверка
всегда идёт после действия, а действие одно.

### Проверка и import static

`assertThat(score).isEqualTo(100)` — проверка AssertJ из статьи 1:
«утверждаю, что балл равен 100». В `assertThat(…)` пишут то, что
получил код. В `isEqualTo(…)` — то, что ты ждёшь. Перепутать трудно:
порядок подсказывают сами слова.

Не сошлось — тест красный, и AssertJ пишет оба значения: что ожидалось
и что получено. Как читать красный отчёт целиком, покажет продолжение
серии.

Откуда `assertThat` без имени класса? Это статический метод класса
`org.assertj.core.api.Assertions`. Полностью вызов выглядел бы так:
`Assertions.assertThat(score)`. Короче его делает строка в начале файла:

```java
import static org.assertj.core.api.Assertions.assertThat;
```

Обычный `import` подключает класс. **`import static`** подключает
статический член класса, метод или константу, и его можно писать без
имени класса. Документация Java советует пользоваться этим скупо, только
для того, что зовёшь постоянно. `assertThat` зовут в каждом тесте,
поэтому так пишут везде.

⚠️ На `assertThat` IDE может предложить несколько вариантов из разных
библиотек. В том же наборе `spring-boot-starter-test` приезжает
**Hamcrest**, ещё одна библиотека проверок. У неё свой `assertThat`
с двумя аргументами, в классе `org.hamcrest.MatcherAssert`. Выберешь
его, и строка `assertThat(score).isEqualTo(100)` не скомпилируется.
Нам нужен `org.assertj.core.api.Assertions`.

### Почему 100, а не DeadlineScore.FULL

У `DeadlineScore` есть константа `FULL = 100`. Велик соблазн написать
проверку через неё. Так короче, и в проверке нет **магического числа** —
числа, смысл которого не объяснён. Вот так неверно, это только для
разбора:

```java
// так не пишем: ожидание взято из проверяемого кода
assertThat(score).isEqualTo(DeadlineScore.FULL);
```

Представь, что кто-то, правя класс, опечатался: `FULL = 10`. Теперь
за работу, сданную вовремя, код даёт 10 баллов. Тест с `FULL` по сути
спрашивает код: «ты вернул столько, сколько сам считаешь полным баллом?»

Код отвечает «да»: 10 равно 10. Тест зелёный, а ошибка уходит в работу.
Тест с числом `100` покраснеет: ждали 100, получили 10.

Ожидание — то, что тест считает правильным ответом. Его записывают
**независимо от кода**, который проверяют: по обещанию, то есть
по строке правила «вовремя — 100». Тест, взявший ожидание
из проверяемого кода, сверяет код с ним же самим. Так ученик проверял бы
контрольную по своему же черновику.

Число в тесте повторяет число в коде нарочно. Обещание записано дважды,
в двух независимых местах, и сборка следит, чтобы записи совпадали.
Это дублирование — не грех, а смысл теста.

🔑 **Ожидание в тесте — из обещания, а не из кода.** Тест, который взял
ожидание из константы, согласится с ошибкой в ней.

С `DEADLINE` дело другое: это не ожидание, а условие, которое тест
задаёт сам. Поэтому константа живёт в самом тесте, а не в проверяемом
классе.

## Часть 3. Четыре поведения, четыре имени

### Остальные тесты

Ещё два теста — на опоздание:

```java
    @Test
    void lateWithinDayGetsHalf() {
        Instant submittedAt = DEADLINE.plus(Duration.ofHours(1));

        int score = DeadlineScore.score(DEADLINE, submittedAt);

        assertThat(score).isEqualTo(50);
    }

    @Test
    @DisplayName("опоздал больше чем на сутки — ноль")
    void lateByMoreThanDayGetsNothing() {
        Instant submittedAt = DEADLINE.plus(Duration.ofDays(2));

        int score = DeadlineScore.score(DEADLINE, submittedAt);

        assertThat(score).isEqualTo(0);
    }
```

Теперь моментов сдачи четыре: за минуту до срока, ровно в срок, через
час и через двое суток. Баллы за них: 100, 100, 50 и 0. Каждый тест
проверяет одно **поведение**: одно обещание правила на одном случае.
Пометку `@DisplayName` над последним разберём ниже.

### Один тест — одно поведение

Почему не один тест с четырьмя проверками подряд? Причин три.

**Первая же несошедшаяся проверка останавливает тест.** AssertJ бросает
ошибку, и строки ниже не выполняются. Сломались два правила — увидишь
одно. Починишь его, и только тогда увидишь второе. Четыре отдельных
теста покажут обе поломки сразу.

**Имя говорит, что нарушено.** Красный тест `scoreWorks` сообщает только
«что-то с баллами». Красный `lateWithinDayGetsHalf` называет нарушенное
обещание ещё до того, как ты открыл код.

**Каждый тест можно запустить отдельно.** Чинишь одно правило —
запускаешь только его тест. Поэтому тесты не должны зависеть друг
от друга. JUnit не обещает даже порядок файла. Порядок у него, как
сказано в документации, «детерминированный, но намеренно неочевидный».
Каждый тест готовит всё сам, общая у них только неизменяемая константа.

Одно поведение — не обязательно одна строка `assertThat`. Если ответ
метода — объект из двух полей, проверок может быть две.

### Имя теста — первое, что ты прочтёшь, когда он упадёт

В песочнице имена — короткая фраза по-английски. Слова пишутся слитно,
каждое следующее с заглавной буквы: случай и что при нём происходит.
`lateWithinDayGetsHalf` значит «опоздал в пределах суток — получает
половину». `onDeadlineIsStillOnTime` — «сдал ровно в срок, и это ещё
вовремя». Слово `test` в имени лишнее: и так понятно, что это тест.

Плохие имена — `test1`, `testScore`, `scoreWorks`. В проекте с сотнями
тестов покраснеет `test3`, и его имя не скажет ничего. Придётся читать
код, только чтобы понять, что проверялось.

У другого стиля имя складывается из трёх частей через подчёркивание:
`метод_Should…_When…`. Это метод, что должно быть и при каком условии.
Стиль длиннее, зато удобен, когда в одном классе тесты нескольких
методов: первая часть имени группирует их по методу. Наш класс проверяет
один метод, `score`, и первая часть повторялась бы в каждом имени.
Поэтому здесь короткий стиль.

В рабочем проекте, наоборот, через подчёркивание названы почти все
тесты. Порядок частей там бывает и другой: метод, потом условие, потом
итог. Живут оба стиля. В чужом проекте пиши так, как принято там.

### @DisplayName — имя для людей

**`@DisplayName`** — пометка JUnit, которая даёт тесту второе имя, для
отчёта. В нём можно то, чего нет в имени метода: пробелы, тире, знаки
препинания, русский язык. В нашем файле она стоит над одним тестом,
чтобы ты увидел разницу. В IDE этот тест подписан
не `lateByMoreThanDayGetsNothing()`, а «опоздал больше чем на сутки — ноль».

Когда она помогает. Когда фразу проще прочитать по-русски, чем собрать
из английских слов. Когда в случае есть числа и условия, которые в имени
метода превращаются в кашу.

Когда мешает. Когда имя метода и так читается: тогда это второе имя,
которое надо держать в согласии с первым. Поменял поведение, поправил
имя метода, забыл про `@DisplayName` — и отчёт врёт.

И главное: Maven русское имя по умолчанию не показывает. В зелёном
журнале у него только классы, а упавший тест он называет именем метода.
Это настраивается, но в песочнице не настроено. Поэтому `@DisplayName`
не заменяет хорошее имя метода, а только дополняет его.

Хороший `@DisplayName` — обещание целиком: случай и исход. «Опоздал
больше чем на сутки» называет только случай. «Опоздал больше чем
на сутки — ноль» говорит и что при нём будет.

В команде русский `@DisplayName` есть у тестов настроек. Там
встречаются оба вида: имя только со случаем и полная фраза, где есть
и случай, и исход.

### Тесты по пунктам задачи

Помнишь раздел «Требования к тестам» из статьи 1? В рабочем проекте
он есть у задач джуна с кодом и обычно начинается с имени класса
и пометки «без Spring». Дальше идут пункты «Тест 1: …», «Тест 2: …»:
в каждом фраза о поведении и что проверить.

Перевести такой раздел в код можно тем, что ты уже знаешь:

* класс называешь ровно как в задаче: по этому имени его найдёт
  ревьюер, а по окончанию `Test` — сборка;
* «без Spring» значит модульный тест, как наш;
* один пункт — один метод: пункт и есть одно поведение;
* имя метода берёшь из фразы пункта, коротким стилем.

Номер пункта — не имя: `test1` в красном отчёте ничего не скажет. Если
задача даёт заготовку теста с именем метода, бери имя как есть.

## Часть 4. Запустить, прочитать зелёное, сломать

### Три способа запуска

* **Один тест** — зелёный треугольник рядом с методом в IDE. Так
  проверяешь то, что пишешь прямо сейчас: секунда, и ответ готов.
  Из командной строки — `./mvnw test -Dtest=DeadlineScoreTest#lateWithinDayGetsHalf`:
  класс, знак `#` и имя метода.
* **Класс** — треугольник рядом с классом или команда
  `./mvnw test -Dtest=DeadlineScoreTest`.
* **Все** — `./mvnw test`. Перед отправкой изменений запускай
  `./mvnw verify`, как в статье 1.

### Зелёный отчёт в IDE

После запуска IDE открывает панель с деревом. В нём класс
`DeadlineScoreTest`, под ним четыре теста с зелёными галочками,
у каждого время в миллисекундах. Рядом сводка: сколько прошло
из скольких. Тест про двое суток подписан русским именем
из `@DisplayName`.

### Зелёный отчёт в Maven

`./mvnw test` в песочнице заканчивается так:

```
[INFO] Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

Тестов пять: четыре наших и `contextLoads` от Initializr. После статьи 1
их было два. Один тест мы переписали, три добавили, и число выросло
ровно на столько, сколько добавили.

Выше в журнале — по строке на каждый класс. Например,
`Running example.testy.score.DeadlineScoreTest`, а под ней итог класса:
`Tests run: 4, …`. Имён тестов в зелёном журнале Maven не пишет, только
классы.

### Каждый тест хоть раз красный

Четыре теста зелёные. Можно ли им верить? Пока нет.

🔑 Главная мысль серии: **зелёному тесту верят, только если видели его
красным.** В статье 1 мы так проверили один тест, теперь проверим каждый
из четырёх. Вот метод, который будем ломать:

```java
    public static int score(Instant deadline, Instant submittedAt) {
        // … проверки на null — в полном примере статьи 1
        if (!submittedAt.isAfter(deadline)) {                   // ровно в срок — ещё вовремя
            return FULL;
        }
        if (!submittedAt.isAfter(deadline.plus(GRACE))) {       // ровно через сутки — ещё половина
            return HALF;
        }
        return NONE;
    }
```

Ломаем по одной строке, и каждый раз — один круг: поменял, запустил
класс, увидел красное, вернул, снова зелёное.

| что сломать | что покраснеет | что скажет |
|---|---|---|
| первый `return FULL;` → `return HALF;` | `beforeDeadlineGetsFull` и `onDeadlineIsStillOnTime` | ждали 100, получили 50 |
| `return HALF;` → `return FULL;` | `lateWithinDayGetsHalf` | ждали 50, получили 100 |
| `return NONE;` → `return HALF;` | `lateByMoreThanDayGetsNothing`, в IDE — «опоздал больше чем на сутки — ноль» | ждали 0, получили 50 |

Только одна поломка за раз. Сломаешь две сразу — и уже не скажешь,
какой тест на какую покраснел.

Что это дало? Каждый тест хоть раз покраснел, и именно на своей поломке.
Первая поломка уронила сразу два теста, и это не повтор. Оба стерегут
полный балл, но в разных точках: до срока и ровно в срок.

А поломку из статьи 1, `isBefore` вместо `!isAfter`, из четырёх поймает
только `onDeadlineIsStillOnTime`. «Раньше срока» и «не позже срока»
различаются только в самом сроке.

💡 Помнишь, как в статье 1 сутки превращали в 23 часа? Эту поломку
не видят и четыре теста: все останутся зелёными. Ни один из них
не сдаёт работу между двадцать третьим и двадцать четвёртым часом
опоздания. Какие случаи брать, чтобы таких дыр не оставалось, расскажет
продолжение серии.

## Проверь себя

Ответь своими словами — вслух или на бумаге. Не получается — перечитай
раздел.

1. Почему тестовый класс и методы можно писать без `public`, а в примерах
   из интернета он есть? Что будет с тестом, где `import org.junit.Test`?
2. Зачем срок вынесен в константу, и что дают ей слова `private`,
   `static` и `final`?
3. Один тест вызывает `DEADLINE.plus(Duration.ofHours(1))`. Изменится ли
   срок в соседнем тесте? Почему?
4. Найди в `lateWithinDayGetsHalf` «дано», «когда» и «тогда». Почему
   в `onDeadlineIsStillOnTime` блоков два?
5. Коллега предлагает писать `isEqualTo(DeadlineScore.FULL)`: «без
   магических чисел». Что станет с таким тестом, если кто-то сделает
   `FULL = 10`?
6. Почему четыре теста лучше одного с четырьмя проверками?
7. Чем `lateWithinDayGetsHalf` лучше `test3`? Когда удобнее имя вида
   `метод_Should…_When…`, и почему `@DisplayName` не заменяет хорошее
   имя метода?
8. Все четыре теста зелёные. Что сделать, чтобы этому зелёному можно было
   верить, и почему ломать нужно по одной строке?

## Что дальше

Тест покраснел: что делать. Читаем отчёт и стек вызовов, ищем в них свою
строку. А потом разбираем ошибку коллеги, которую четыре теста из этой
статьи пропустили. Это следующая статья серии.

## Пример целиком — с импортами

Учебный пример живёт в песочнице `testy` из статьи 1. Как её собрать,
сказано там, в «Примере целиком». `DeadlineScore` и `ManualCheck`
остаются такими, как в статье 1, поэтому здесь их нет.
`DeadlineScoreTest` целиком заменяет однотестовый из статьи 1, по тому
же пути. `TestyApplicationTests` не трогай.

```java
// src/test/java/example/testy/score/DeadlineScoreTest.java
package example.testy.score;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import java.time.Duration;
import java.time.Instant;

import static org.assertj.core.api.Assertions.assertThat;

class DeadlineScoreTest {

    // полночь 13 октября по Москве
    private static final Instant DEADLINE = Instant.parse("2026-10-12T21:00:00Z");

    @Test
    void beforeDeadlineGetsFull() {
        Instant submittedAt = DEADLINE.minus(Duration.ofMinutes(1));

        int score = DeadlineScore.score(DEADLINE, submittedAt);

        assertThat(score).isEqualTo(100);
    }

    @Test
    void onDeadlineIsStillOnTime() {
        int score = DeadlineScore.score(DEADLINE, DEADLINE);

        assertThat(score).isEqualTo(100);
    }

    @Test
    void lateWithinDayGetsHalf() {
        Instant submittedAt = DEADLINE.plus(Duration.ofHours(1));

        int score = DeadlineScore.score(DEADLINE, submittedAt);

        assertThat(score).isEqualTo(50);
    }

    @Test
    @DisplayName("опоздал больше чем на сутки — ноль")
    void lateByMoreThanDayGetsNothing() {
        Instant submittedAt = DEADLINE.plus(Duration.ofDays(2));

        int score = DeadlineScore.score(DEADLINE, submittedAt);

        assertThat(score).isEqualTo(0);
    }
}
```

Сделай руками:

1. `./mvnw test` — `Tests run: 5, Failures: 0, Errors: 0, Skipped: 0`
   и `BUILD SUCCESS`.
2. В IDE запусти один тест треугольником у метода, потом весь класс.
   Найди в дереве русское имя. Из командной строки:
   `-Dtest=DeadlineScoreTest#lateWithinDayGetsHalf` даст `Tests run: 1`,
   `-Dtest=DeadlineScoreTest` — `Tests run: 4`.
3. Три поломки из таблицы части 4 — по одной, каждый раз возвращая
   строку на место.
4. Сделай `FULL = 10`. Покраснеют `beforeDeadlineGetsFull`
   и `onDeadlineIsStillOnTime`: ждали 100, получили 10. Верни.
5. Поменяй в `GRACE` 24 часа на 23 — всё зелёное. Верни и запомни эту
   дыру: к ней вернёмся в продолжении серии.

Теперь у каждого из четырёх тестов есть то, ради чего его писали: он
умеет покраснеть, и краснеет ровно тогда, когда нарушено его обещание.
